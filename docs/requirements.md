# Требования к системе бронирования коворкинга

## 1. Роли пользователей

### Гость
- Что делает: просматривает список комнат (вместимость, цена), проверяет доступность на даты.
- Доступ к данным: только публичная информация о комнатах. Персональные данные и брони недоступны, бронирование запрещено.

### Клиент (зарегистрированный пользователь)
- Что делает: создаёт/отменяет **свои** брони, оплачивает, смотрит историю броней и платежей.
- Доступ к данным: свои брони и платежи — полностью; комнаты — публичные данные; чужие брони и данные других пользователей — недоступны.

### Администратор
- Что делает: управляет комнатами (создание, деактивация), пользователями, разрешает конфликты, оформляет возвраты, видит все брони и платежи.
- Доступ к данным: все данные, кроме паролей (хранятся как хэш).

## 2. Сценарии использования

### Сценарий 1. Бронирование комнаты
- Роль: Клиент
- Шаги: 1) выбирает комнату по дате/вместимости; 2) система показывает свободные интервалы; 3) вводит `start_time`/`end_time` и подтверждает; 4) система создаёт бронь со статусом `pending`.
- Результат: бронь сохранена, интервал занят.
- Граничный случай: два клиента одновременно бронируют один интервал — одна бронь должна упасть с ошибкой конфликта (constraint).

### Сценарий 2. Оплата брони
- Роль: Клиент
- Шаги: 1) открывает свою бронь; 2) инициирует оплату; 3) система фиксирует платёж.
- Результат: бронь → `confirmed`, платёж `status=paid`.
- Граничный случай: **просроченная оплата** — если оплата не поступила в течение 30 минут, бронь автоматически отменяется.

### Сценарий 3. Отмена брони клиентом
- Роль: Клиент
- Шаги: 1) открывает бронь; 2) нажимает «отменить»; 3) подтверждает.
- Результат: статус `cancelled`, слот освобождается.
- Граничный случай: **отмена после оплаты** — если до начала > 24 ч, возврат 100 %; иначе 50 %.

### Сценарий 4. Двойная бронь
- Роль: Клиент
- Шаги: 1) пытается забронировать интервал, который пересекается с активной бронью другой комнаты/пользователя на тот же слот.
- Результат: система отклоняет с ошибкой нарушения ограничения (exclusion constraint).
- Граничный случай: бронь «встык» (`end_time` = чужой `start_time`) — **разрешена**, пересечением не считается.

### Сценарий 5. Просмотр доступности гостем
- Роль: Гость
- Шаги: 1) выбирает дату; 2) видит список комнат с занятыми/свободными слотами.
- Результат: только публичная информация, без ПДн.

### Сценарий 6. Управление комнатами
- Роль: Администратор
- Шаги: 1) создаёт комнату; 2) при необходимости деактивирует (`is_active=false`).
- Результат: новые брони на неактивную комнату запрещены, существующие сохраняются.
- Граничный случай: попытка удалить комнату с активными бронями — блокируется (`ON DELETE RESTRICT`).

## 3. Сущности и атрибуты

| Сущность | Атрибуты | Предполагаемый ключ | Тип ключа |
|---|---|---|---|
| app_user | user_id, email, full_name, phone, role, password_hash, created_at | user_id (суррогатный); email — естественный кандидат | суррогатный |
| room | room_id, code, name, capacity, hourly_rate, is_active, created_at | room_id (суррогатный); code — естественный кандидат | суррогатный |
| booking | booking_id, room_id, user_id, start_time, end_time, status, created_at | booking_id | суррогатный |
| payment | payment_id, booking_id, amount, status, paid_at, created_at | payment_id | суррогатный |

## 4. Связи и кардинальности

- `app_user 1 : N booking` — у пользователя много броней, у брони ровно один пользователь. Участие обязательное со стороны `booking`.
- `room 1 : N booking` — у комнаты много броней, у брони ровно одна комната. Обязательное со стороны `booking`.
- `booking 1 : 1 payment` — у брони не более одного платежа; платёж всегда относится к одной брони. Со стороны `payment` участие обязательное, со стороны `booking` — опциональное (бронь может быть не оплачена).

## 5. Бизнес-правила и ограничения

| № | Правило                                                                          | Как проверяется |
|---|----------------------------------------------------------------------------------|---|
| 5.1 | В одной комнате не может быть двух **активных** броней с пересечением по времени | `EXCLUDE USING gist (room_id WITH =, tstzrange(start_time, end_time) WITH &&) WHERE (status IN ('pending','confirmed'))` |
| 5.2 | Время окончания брони должно быть строго больше времени её начала.               | `CHECK (end_time > start_time)` |
| 5.3 | Вместимость комнаты должна быть положительным числом                             | `CHECK (capacity > 0)` |
| 5.4 | Почасовая ставка аренды не может быть отрицательной                                                               | `CHECK (hourly_rate >= 0)` |
| 5.5 | email содержит `@`                                                               | `CHECK (position('@' in email) > 1)` |
| 5.6 | Нельзя бронировать в прошлом                                                     | `CHECK (start_time > created_at)` |
| 5.7 | Максимальная длительность брони — 12 часов                                       | `CHECK (end_time - start_time <= interval '12 hours')` |
| 5.8 | Комнату нельзя удалить, пока есть брони                                          | `FOREIGN KEY ... ON DELETE RESTRICT` |
| 5.9 | Бронь можно создать только на активную комнату                                   | проверка запросом/триггером (`room.is_active = true`) |
| 5.10 | Возврат при отмене: > 24 ч до старта — 100 %, иначе 50 %                         | проверяется SQL-запросом при возврате / триггером |

## 6. Профиль нагрузки

**OLTP** (короткие транзакции, высокая частота записи):
- создание брони, отмена, оплата;
- проверка доступности (точечные `SELECT` по индексу `room_id, tstzrange`).

**OLAP** (периодические агрегаты, реже):
- отчёты по загрузке и выручке за месяц;
- воронка отмен и возвратов.

**Ожидаемые объёмы (порядок величин):**
- `room`: десятки–сотни строк;
- `app_user`: тысячи–десятки тысяч;
- `booking`: сотни тысяч в год;
- `payment`: сотни тысяч в год.

## 7. Нефункциональные требования

- **Доступность:** 99.5 % в рабочие часы.
- **RPO:** ≤ 15 минут. **RTO:** ≤ 1 час.
- **Безопасность:**
    - RLS: клиент видит **только свои** брони; администратор — все; гость — только публичную информацию о комнатах.
    - PII (email, телефон) доступны владельцу и администратору.
